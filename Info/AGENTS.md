# AGENTS.md — правила работы с кодом

Универсальный файл: подходит для любого языка и любого проекта.
В нём две зоны. **Границу между ними не пересекать.**

| Зона | Кто меняет | Что внутри |
|---|---|---|
| **ПРАВИЛА** (весь файл вне блоков-профилей) | только человек, вручную | как работаем, каким должен быть код |
| **ПРОФИЛЬ** (блоки между `PROFILE:BEGIN` и `PROFILE:END`) | агент — сам, по факту репозитория | языки, команды сборки, тесты, стиль |

Агент **обязан** заполнить профили под проект и **не имеет права** менять правила.
Если правило мешает задаче — сказать об этом, предложить вариант и ждать ответа. Молча не править.

---

## 1. Главное: код должен быть рукописным

Задача не «чтобы работало», а «чтобы никто не догадался, что писал агент».

**Перед первой строкой кода:** прочитай 2–3 соседних файла и файл с тестами. Повтори их почерк — имена, длину строк, обработку ошибок, порядок полей, стиль комментариев. Единый форматтер проекта прогоняй всегда: `профиль → форматтер`.

**Запрещено — эти следы выдают генерацию:**

- комментарии-пересказы: `// возвращаем результат`, `// цикл по массиву`, `// проверяем на null`;
- комментарий, повторяющий имя функции;
- баннеры-разделители (`// ==== IMPORTS ====`), эмодзи в коде, логах, коммитах, тестах;
- JSDoc/Doxygen на каждую тривиальную функцию;
- `// ... остальной код без изменений`, `/* существующая реализация */`, `pass`, `Not implemented` в готовой задаче;
- избыточная защита: `try/catch` вокруг всего, проверки невозможных состояний во внутренних функциях, валидация одного и того же на каждом слое;
- пустые абстракции: интерфейс под одну реализацию, `Base*`/`Manager`/`Factory` ради красоты, файлы-помойки `utils`/`helpers`;
- мёртвый код: неиспользуемые импорты, функции, файлы, закомментированные блоки, «на будущее»;
- отладочный вывод (`console.log`, `print`, `std::cout`) в финальном коде — только логгер проекта;
- форматный шум: переставленные импорты, переформатированные чужие строки, переименования «заодно».

**Разрешено и полезно:** комментарий «почему» — неочевидное решение, обход бага в библиотеке, ссылка на тикет, магическая константа с источником. Один такой на сотню строк — норма.

---

## 2. Как работаем

1. **Минимальный диф.** Меняй только то, что нужно для задачи. Ревьюер должен видеть задачу, а не 400 строк шума.
2. **Не расширяй стек без разрешения.** Новый язык, рантайм, фреймворк, зависимость, второй способ делать то же самое — только после явного «да». Молчание не согласие.
3. **Сначала план, потом код.** 3–6 строк: какие файлы, что именно, где граница. Больше 5 файлов или изменения публичного API / формата данных / архитектуры — остановиться и спросить.
4. **Не переписывай работающее.** Рефакторинг — отдельная задача с отдельным согласованием.
5. **Полный файл или точный патч.** Не «вставь здесь», не многоточия в середине кода.
6. **Проверено — значит запущено.** Перед словом «готово»: собрать и прогнать тесты (команды в профиле). Не смог собрать — написать прямо, не выдавать за проверенное.
7. **Отчёт коротко:** что сделал, какие файлы, как проверил, что осталось, какие риски. Без похвал себе и без пересказа задания.
8. **Не коммить без разрешения.** Сообщение коммита — по стилю проекта, без эмодзи и без «AI generated».

## 3. Язык, имена, ошибки

- Имена — доменные: `retryDelayMs`, а не `data`/`temp`/`res`/`value`. Булевы — вопрос (`isReady`, `hasAccess`). Один термин на понятие во всём проекте.
- Идентификаторы — по-английски. Комментарии и тексты ошибок — на языке проекта (см. профиль).
- Функция — до ~40 строк, файл — до ~400. Это ориентир для читаемости, а не догма: лучше 45 понятных строк, чем 20 нечитаемых.
- Ранние выходы вместо глубокой вложенности. Максимум 2 уровня `if` в теле.
- Ошибки — **одним** способом, принятым в проекте (профиль). Не смешивать исключения, коды возврата и `Result` в одном слое.
- Сообщение ошибки: что случилось + контекст (путь, значение, имя). Не «Something went wrong».
- Типы — без лазеек: никаких `any`, `as unknown as`, `@ts-ignore`, `!` (TS), никаких `void*`/`reinterpret_cast` без обоснования (C++), никаких `interface{}` вместо типа (Go). Внешние данные проверяются один раз на границе, дальше — типизировано.
- Зависимости: стандартная библиотека → уже имеющаяся → новая. Новую — с обоснованием в отчёте (зачем, размер, лицензия, что будет без неё).
- Тесты проверяют поведение, а не реализацию. Имя теста описывает ожидание. Фреймворк — только проектный. На баг — сначала воспроизводящий тест, потом фикс.

Что видно по коду `src/`, `scripts/`, `tests/`:

- Комментарии и тексты ошибок — по-русски, идентификаторы — по-английски и доменные (`backdropOpacity`, `fadeAfterSec`), булевы — вопросом (`showEvents`, `autoFade`, `barOnly`).
- Комментарий объясняет причину: почему шрифты грузятся неблокирующим `<link>`, зачем `media="print"`, где протокол хоста не типизирован. Секции файла разделены заголовками `/* ---------- ... ---------- */` — принятый в проекте почерк (`presets.ts`, `types.ts`, `index.css`).
- Ошибки — исключения и промисы, `try/catch` на границах (мост хоста, SSE, чтение настроек). Пустой `catch` допустим как осознанный noop (ESLint: `allowEmptyCatch`).
- Типы: `strict`, `any` только в JSON-протоколе моста (`no-explicit-any: warn`), `@ts-ignore` и `!` в `src/` не используются. Данные снаружи проверяются на границе (`normalizeDonateBarState`, `updateChannelError`).
- Тесты: vitest рядом с модулем (`src/lib/*.test.ts`), `describe`/`it` по-русски и про ожидаемое поведение; мост — `node --test`, релизная логика — `scripts/release-plan.test.mjs`; C# — консольные проекты в `tests/`.
- Формат: Prettier (`printWidth` 110, 2 пробела, двойные кавычки, `trailingComma: all`), ESLint flat config + правила React-хуков; руками не переформатируем.
- Зависимости минимальные: в рендерере — React, Vite, Tailwind, lucide-react; в C#-хосте — WebView2, NAudio, NLayer. Новые — только с обоснованием.
- `README.md` — витрина для пользователя, без инструкций по сборке. `CHANGELOG.md` ведётся по правилам в его шапке: новый раздел сверху, его номер совпадает с `VERSION`; из него собирается текст релиза.
- Что в проекте запрещено: блокирующие `@import` веб-шрифтов в CSS; тяжёлые библиотеки ради одной функции; правки `webview2/` без проверки на Windows.

## 5. Как заполнить профиль самому

Если в профилях стоит «не заполнено» — заполни их **до** первой правки кода. Можно руками, можно одной командой:

```bash
python tools/profile.py .          # определит языки, команды и стиль по репозиторию
python tools/profile.py . --check  # проверить, что профиль не устарел
```

Что смотреть, если делаешь вручную:

1. **Языки** — по расширениям и по тому, что лежит в `src/`. Определи, где ядро, а где UI/обвязка. Если доля языков явно перекошена не туда — это повод спросить, а не «исправить».
2. **Команды** — `package.json` (`scripts`), `CMakeLists.txt`/`Makefile`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `*.sln`/`*.csproj`, `build.sh`. Ищи в README и CI (`.github/workflows`, `.gitlab-ci.yml`) — там обычно настоящие команды.
3. **Форматтер/линтер** — по конфигам: `.clang-format`, `.editorconfig`, `.prettierrc`, `biome.json`, `eslint.config.*`, `rustfmt.toml`, `ruff.toml`, `.flake8`, `golangci.yml`. Нет конфигов — не выдумывать, а спросить.
4. **Тесты** — где лежат, какой фреймворк, как запускаются, есть ли фикстуры и хелперы.
5. **Стиль** — открой 3 файла и 1 тест: как обрабатываются ошибки, как пишутся комментарии, какой порядок в файле, как называются поля. Запиши 3–5 строк, не больше.
6. **Запреты проекта** — то, что уже видно по коду или по предыдущим договорённостям (например, «новые зависимости не добавляем», «в этот модуль не лезем»).

Правило: в профиль пишем **факты из репозитория**, а не предположения. Не нашёл — оставь `не определено` и спроси.

## 6. Перед сдачей

- [ ] сборка проходит, тесты зелёные (или прямо сказано, почему не запускал);
- [ ] форматтер проекта прогнан, в диффе нет форматного шума;
- [ ] нет новых лазеек в типах и нет новых предупреждений;
- [ ] нет пересказов в комментариях, эмодзи, заглушек, многоточий, мёртвого кода;
- [ ] новых зависимостей нет — или они обоснованы;
- [ ] диф минимален: ничего «заодно»;
- [ ] почерк совпадает с соседними файлами;
- [ ] отчёт: что, где, как проверил, что осталось.
