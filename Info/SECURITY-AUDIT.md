# Аудит безопасности — YawaChat (WebView2-оболочка)

Дата: 2026-09-25
Область: `webview2/*.cs` (C#/.NET 8-хост), `src/` (рендерер), CI-пайплайны.
Повторная проверка версии 2.1.6: проверены TLS-подключение, границы
доверия WebView2, хранение секретов и конфигурация защиты релизной сборки.
Метод: ручной прогон кода (хост + рендерер + workflows), проверка границ
доверия: **чат-площадки → коннекторы → лента/оверлей/OBS**,
**рендерер → JSON-RPC-мост → хост → ОС**, **файлы и сеть на диске**.

Пункты, которые **не являются** уязвимостями, но были проверены:
- OAuth: Twitch — Device Code Flow без локального слушателя. VK Видео Live
  подключается только как публичный читатель и OAuth для него не используется.
- WebView2: контекстные меню, DevTools и быстрые клавиши браузера отключены;
  рендерер не уходит со своей страницы; падение рендерера восстанавливается.
- Коннекторы: токены в URL не передаются (кроме штатных заголовков/Bearer);
  ответы площадок парсятся с защитой от неизвестных форматов.
- Установка WebView2: официальный установщик Microsoft по HTTPS, с
  подтверждением результата.
- Мост TikTok: Node-процесс запускается без шелла (аргументы не интерпретируются
  `cmd.exe`), ввод — JSON по stdin.

## Детали и что сделано

### S1. Twitch IRC: отключённая проверка TLS (Критично)

`TwitchIrcConnector` (webview2/Connectors.cs) ставил
`RemoteCertificateValidationCallback = (_, _, _, _) => true` — соединение
принимало **любой** сертификат. По этому сокету ходит `PASS oauth:<токен бота>`:
в сети с перехватом (публичный Wi-Fi, вредоносный провайдер) токен утек бы, а
в чат можно было подмешать сообщения от имени бота.

**Исправлено в 2.1.6:** всегда используется штатная строгая проверка
сертификата; запасное соединение с отключённой проверкой удалено. Если сеть
подменяет сертификат (в том числе при локальной TLS-инспекции), вход с токеном
не продолжается. Это намеренное поведение: безопасность учётных данных важнее
автоматического обхода проверки.

### S2. `shell.openExternal` (Высокая)

Хост запускал любую строку из рендерера:
`Process.Start(new ProcessStartInfo(url) { UseShellExecute = true })`.
При любом сценарии, где в рендерер попало чужой код (XSS через стороннюю
библиотеку, подмена dist-файла на диске), это был прямой запуск произвольной
программы: `powershell -c …`, `file://`, `ms-settings:` и т.д.

**Исправлено:** хост открывает в системном браузере только абсолютные
`http/https`-адреса (`HostApi.IsWebUrl`). Легитимные сценарии (ссылки поддержки, страницы площадок и ссылка виджета)
остаются в пределах http/https.

### S3. Открытые токены в settings.json (Высокая)

В `%LOCALAPPDATA%\YawaChat\settings.json` открытым текстом лежали:
`botToken:twitch` (access token) и `botRefresh:twitch` (refresh token —
позволяет получать новые access-токены **вечно**). Любой процесс от имени
пользователя мог их прочитать. Старые VK-бот-настройки теперь удаляются при
первом запуске версии 2.1.2; VK-коннектор не хранит и не использует токены.

**Исправлено:** новые классы `SettingsCrypto` (webview2/SettingsCrypto.cs) —
DPAPI (Data Protection API, режим CurrentUser) + соль приложения. Токены в
файле хранятся как `yawaenc1:<Base64>`; расшифровать может только тот же
пользователь Windows. Миграция прозрачная: старые открытые значения читаются
как есть и шифруются при первом же сохранении. В памяти хоста значения
остаются обычными строками (кэш не перешифровывается, двойное шифрование
исключено — шифруется копия при записи).

### S4. Чужие URL картинок из чата (Средняя)

Разбор текста чата превращал литеральный токен `[[e|URL|имя]]` в `<img>`.
Токен генерирует хост для настоящих эмоутов, но зритель мог написать эти
символы САМ в сообщении — и страница отправила бы запрос по произвольному
адресу (отслеживание зрителя, сторонние ресурсы). Аватары и значки площадок
тоже уходили в `<img src>` без проверки.

**Исправлено:** `safeImageSrc()` (src/lib/emotes.ts) — картинки чата,
аватары и значки загружаются только по `http/https`; непонятные адреса
заменяются текстовой заглушкой. Точки применения: `parseMessage` (эмодзи-токены),
`Avatar` (ChatFeed.tsx), `ChatBadges` (badges.tsx).

### S5. Навигация WebView2 (Средняя)

Проверка «можно ли открыть адрес в браузере» была
`target.StartsWith("http")` — проходили и поддельные схемы.
**Исправлено:** `Program.IsWebUrl` — строгая проверка `Uri.Scheme`
(http/https) в `NavigationStarting`, `NewWindowRequested` и мосте
`shell.openExternal`.

### S6. Device code в журнале (Низкая)

`oauth.log` получал строку с кодом активации Twitch. Код даёт вход в аккаунт
на время его действия (до 15 минут), поэтому пишется только его длина.

## Защита готового exe от декомпиляции (заказ №2)

Проблема: single-file exe .NET — это IL-код, который декompiler
(ILSpy/dnSpy) раскрывает обратно до читаемого C# за секунды: вся логика
коннекторов, OAuth, модерации и TTS.

**Решение — Obfuscar (MIT) в релизном пайплайне между build и single-file
publish** (`scripts/obfuscate.ps1`, шаги в `.github/workflows/release.yml`):

- переименование **всех** типов, методов и полей (публичных и внутренних) —
  `TwitchIrcConnector`, `AppAuth`, `HostApi` и т.д. превращаются в `a_0`, `b_1`…;
- шифрование строковых констант (XOR) — тексты ошибок, URL, client_id
  не читаются `strings`/декомпилятором;
- имена **свойств** не трогаются — это JSON-протокол с рендерером
  (анонимные типы и `ChannelSubInput` сериализуются через рефлексию);
- встроенные ресурсы (интерфейс, Node.js, TikTok-мост) сохраняются —
  exe остаётся самодостаточным.

Усиление пайплайна в 2.1.6: сокрытие строк и дополнительная метка для
стандартных средств IL-дизассемблировки включены явно; на сборке проверяются переименование нескольких
ключевых компонентов, отсутствие контрольных строк в открытом виде и наличие
встроенного интерфейса. Любая неудача останавливает выпуск. Release-проверка
также отклоняет сборку с отладочными символами.

Гарантии корректности:

1. скрипт **проверяет** результат до замены: сборка читается как валидная
   .NET-сборка, свойства JSON-протокола на месте, ключевые имена скрыты —
   иначе сборка падает и релиз не выходит;
2. тот же шаг прогоняется в CI на каждом пуше (`.github/workflows/ci.yml`),
   поэтому проблема пайплайна обнаруживается до релиза;
3. после publish проверяются PE-заголовок, размер и отсутствие отладочных символов.

**Важно по пункту 5 задания:** защита выполняется только в CI при выпуске
релиза. Репозиторий содержит лишь скрипт и конфигурацию обфускатора — ни
одного защищённого артефакта. Клонировать, читать исходники и собирать
локально можно как раньше; локальные dev-сборки обфускацией не покрываются.

Честные границы защиты: обфускация — высокий барьер, а не шифр. Упорный
анализатор всё ещё может восстановить структуру; JS-интерфейс (dist) и
встроенный TikTok-мост по сути остаются открытыми — как и в любом
web-приложении, они видны и на машине пользователя. Ценные секреты
(токены) в exe и на диске больше не лежат в открытом виде (S3), а сами
client_id площадок публичны по определению. Для полного закрытия осталось
только Native AOT — сейчас он несовместим с используемой сериализацией JSON
(сотни вызовов через anonymous types) и требует большой переработки;
выбрана обфускация как надёжный минимум без риска для стабильности.

## Выполнено в версии 2.1.6

- S9: в desktop-версии сохранённый список подключений защищается при записи,
  а WebView localStorage больше не получает отдельную открытую копию. При
  первом запуске старое дублирующее значение удаляется по мере загрузки
  настроек; прежний формат настроек хоста автоматически сохраняется заново.
- S10: внутренняя навигация ограничена точной страницей приложения, а
  сообщения JSON-моста принимаются только от доверенной страницы. Эти
  проверки выполняются при навигации и получении сообщений и не добавляют
  работу к обработке чата/рендерингу.

## Рекомендации (не сделано в этом изменении)

1. **Code signing** — в workflow уже есть шаг подписи `CERT_PFX_BASE64`;
   без подписи SmartScreen будет предупреждать о каждом новом exe.
2. **Ограничение WebView2 user-data folder**: при желании можно запретить
   запуск второго экземпляра приложения (сейчас второй запуск делит профиль
   WebView2 с первым — работает, но не гарантировано Microsoft).
3. **Обновление WebView2 SDK** в csproj (1.0.2903.40) — при появлении новых
   версий пакета.
